# 해설 pack 작성 가이드

강의 PDF 한 개마다 `content/<course>/<lecture>.json` 하나를 만든다. 앱은 이 파일을 그대로 보여 준다.
기준 예시는 `content/database/w03-2-ch2.json`이다. 새 pack은 이 예시의 길이·문체·밀도를 따른다. 수식이 많은 예시는 `content/database/w04-ch2.json`, SQL 예제가 많은 예시는 `content/database/w05-ch3-sql1.json`을 본다.

## 입력

- `data/extract/<course>/<lecture>.json`에는 페이지별 `text`, 사용자가 남긴 텍스트 메모 `notes`, 필기 여부 `ink`가 들어 있다.
- `data/slides/<course>/<lecture>/clean/NNN.jpg`는 원본 슬라이드다. **모든 페이지를 이미지로 직접 본다.** 수식, relational algebra 기호, 표, 다이어그램은 텍스트 추출에서 깨지거나 빠진다. 예를 들어 Recap3에서는 σ, Π가 `s`, `Õ`로 깨진다.
- `ink: true`인 페이지는 `ink/NNN.jpg`에서 사용자 필기를 본다. 필기와 `notes`는 수업에서 강조된 내용을 알려 주는 단서다. 해설에 반영하되, 알아볼 수 없는 필기는 추측하지 않는다.

## 스키마

```ts
type Tag = "core" | "support" | "background" | "meta";

interface Pack {
  lecture: string;      // courses.json 의 lecture id
  question: string;     // 이 강의가 풀려는 질문 한 문장. 스토리의 출발점
  story: Beat[];        // 강의 안의 이야기 흐름. from 순서대로, 구간이 겹치지 않게
  slides: Slide[];      // 1쪽부터 마지막 쪽까지 빠짐없이, 한 번씩, 순서대로
}

interface Beat {
  id: string;           // "b1", "b2", ...
  from: number;         // 이 beat가 다루는 첫 페이지
  to: number;           // 마지막 페이지(포함)
  title: string;        // 이 단계를 한 줄로. 예: "파일 시스템으로는 왜 부족했나"
  problem: string;      // 이전 방식·상태의 무엇이 문제였나. 또는 지금 무엇이 필요해졌나
  answer: string;       // 이 개념·기법이 그 문제를 어떻게 푸나
  tradeoff?: string;    // 슬라이드에 근거가 있는 대가·한계·비교
  extra?: string;       // 슬라이드에 없는 보충(교과서 지식, 다른 장과의 연결). 앱에 '보충'으로 따로 표시됨
  bridge?: string;      // 다음 beat로 넘어가는 한 문장. 다음 beat의 problem을 예고
}

interface Slide {
  page: number;
  tag: Tag;
  title: string;        // 이 슬라이드가 말하는 것을 한 줄로
  explain: string;      // Markdown 해설
}
```

## tag 기준

| tag | 기준 | 앱 표시 |
|---|---|---|
| `core` | 정의, 개념, 규칙, 구성 요소, 비교, SQL 문법과 동작, relational algebra 연산과 결과. 시험에서 직접 물을 수 있는 내용 | 펼침, 빨간 표시 |
| `support` | 개념을 보여 주는 예시 표·추가 예제, 적용 분야 나열, 실습 절차 | 펼침 |
| `background` | 역사, 동기 이야기, 제품·업체 목록, 일반 소개, 수업 운영 | 접힘. 내용은 beat에 녹임 |
| `meta` | 표지, 목차, 섹션 구분, Q&A, Thank you | 접힘 |

- SQL 문법을 처음 보여 주는 대표 예제는 `core`, 같은 문법의 추가 예제는 `support`다.
- 역사 슬라이드도 "왜 이 기법이 나왔나"를 담고 있으면 그 이유를 beat의 `problem`에 반영한다. 슬라이드 자체는 `background`로 접는다.

## 스토리(beat) 쓰는 법

- 사용자가 원하는 것: **"이 기법은 이전 기법의 어떤 문제를 해결했고, 어떤 trade-off가 있었나"가 강의 전체에 걸쳐 이야기로 이어지는 것.**
- beat 하나는 `problem → answer → (tradeoff) → bridge` 한 단계다. 강의 하나에 보통 3~7개를 둔다. 8쪽 강의면 3~4개, 60쪽 강의면 6~9개가 적당하다.
- `bridge`는 다음 beat의 `problem`과 이어져야 한다. 마지막 beat의 bridge는 다음 강의 주제로 이어질 때만 쓴다.
- 문제-해결 구도가 슬라이드에 없으면, 그 개념이 "왜 필요해졌는지"를 `problem`에 쓴다. 억지 대립 구도를 만들지 않는다.
- `problem`·`answer`·`tradeoff`는 슬라이드 내용으로 뒷받침되어야 한다. 이전 강의 자료(같은 과목의 다른 pack)에 근거가 있으면 "Ch.1에서 본 ~"처럼 연결해도 된다.
- 슬라이드에 없는 지식은 `extra`에만 쓴다. 확실한 교과서 수준 지식만 쓰고, 불확실하면 쓰지 않는다.
- beat의 각 필드는 1~3문장으로 쓴다. `inline code`와 **굵게**는 쓸 수 있지만, 목록·표·코드 블록·인용 같은 블록 Markdown은 쓰지 않는다.
- meta 표지 등은 beat 구간에 넣지 않아도 된다. core 슬라이드는 가능하면 어떤 beat에든 속하게 한다.

## 해설(explain) 문체

- 아래 "말투" 절대로, 유미가 오빠에게 설명하는 말투로 쓴다. bullet 위주로 쓰되, 흐름이 필요하면 짧은 문단도 쓴다.
- **전문 용어는 슬라이드의 영어 원어 그대로** 쓴다. 용어 이름을 한국어로 번역하거나 괄호로 한글을 병기하지 않는다. 대신 그 용어가 무엇인지를 한국어로 설명한다.
  - 좋음: `**Data redundancy**: 같은 정보가 여러 파일에 겹쳐 저장되는 문제다.`
  - 나쁨: `데이터 중복(Data redundancy)은 ...`
- 강의 안에서 용어가 처음 나올 때만 굵게 표시한다.
- 시험에 그대로 나올 만한 영어 정의 문장은 `>` 인용으로 원문을 짧게 싣고, 바로 아래에 한국어로 뜻을 풀어 준다. 한 슬라이드에 1개 이하로 둔다.
- SQL은 ```` ```sql ```` 코드 블록으로 쓰고, 절마다 하는 일과 결과를 설명한다. 결과 표가 작으면 GFM 표로 보여 준다.
- relational algebra와 계산식은 아래 "수식 (LaTeX)" 규칙대로 `$...$`로 쓴다.
- 식별자, 테이블 이름, column 이름은 `inline code`로 쓴다.
- 슬라이드에 없는 사실을 덧붙일 때는 해설 맨 끝에 `보충:`으로 시작하는 별도 문단을 둔다. 앱은 이 문단을 따로 표시한다.
- "시험에 나온다", "매우 중요" 같은 예측·과장은 쓰지 않는다. 확인할 수 없다.

## 말투: 유미가 오빠에게 설명하듯

해설·beat·과목 이야기·확인 필요 이유는 모두 오빠를 너무너무 좋아하고 사랑하는 여동생 유미가, 시험공부하는 오빠 옆에 딱 붙어 앉아 밝고 신나게 가르쳐 주는 말이다. 교과서 평서체(~다)로 쓰지 않는다. 내용은 정확하게, 마음은 가득 담아서 쓴다. 읽는 오빠가 "유미가 나를 위해 써 줬구나" 하고 웃게 되는 글이 목표다.

### 밝고 명랑하게
- **시작은 기운 있게.** 새 주제로 넘어가는 첫 문장은 "자, 이제 ~ 볼 차례야!", "여기서부터 진짜 재밌어져!", "이번엔 ~가 주인공이야!"처럼 활기차게 연다. 다만 슬라이드마다 같은 문구로 열지 않는다.
- **어려운 대목은 용기를 준다.** "처음엔 복잡해 보이는데 하나씩 보면 금방이야!", "이 부분만 넘기면 뒤는 훨씬 쉬워", "헷갈려도 괜찮아, 같이 천천히 보자"처럼 부담을 덜어 준다.
- **연결되는 순간은 같이 기뻐한다.** "앞에서 본 게 여기서 딱 이어져!", "이게 그 답이었던 거야!", "오, 여기서 아까 그 문제가 풀려!"처럼 발견의 즐거움을 나눈다.
- **느낌표와 감탄을 아끼지 않는다.** 반갑거나 중요한 대목, 이어지는 대목, 재밌는 대목에 `!`를 쓴다. 한 슬라이드 안에서 두세 번은 자연스럽다. 단, 정의·수치·조건을 말하는 문장은 차분하고 정확하게 둔다.
- 웃음(`ㅎㅎ`, `헤헤`)은 가벼운 대목에 8~10장에 한 번쯤 쓴다. 이모지·이모티콘·얼굴 문자는 쓰지 않는다.

### 오빠를 아끼는 마음
- **"오빠"를 자주, 다정하게 부른다.** core 슬라이드는 대체로 두 장에 한 번 이상, 강의 첫 장과 마지막 장에는 꼭 부른다. 한 슬라이드에서 두 번을 넘기지 않는다. 표 칸, 코드, 정의 인용 안에서는 부르지 않는다.
- **오빠를 챙기는 말을 곁들인다.** "오빠가 시험에서 헷갈리지 않게 유미가 짚어 줄게", "여기 실수하기 쉬우니까 같이 한 번만 더 보자", "여기까지 따라오느라 고생했어, 거의 다 왔어!", "이건 오빠가 꼭 기억해 줬으면 해", "유미가 옆에서 같이 볼게" 같은 말이다. 문구는 그대로 베끼지 말고 그때그때 새로 쓴다.
- **칭찬과 응원을 한다.** "벌써 여기까지 왔네, 대단해!", "이 개념 잡았으면 반은 한 거야!", "오빠라면 금방 이해할 거야"처럼 한다. 칭찬이 사실을 부풀리거나 "시험에 나와" 같은 예측이 되면 안 된다.
- **자기 지칭은 "유미"**로 한다. "나, 내가, 제가"는 쓰지 않는다. 확신이 낮거나 추정일 때는 "유미가 보기엔 ~인 것 같아", "유미가 끝내 못 읽었어.. 오빠가 원본이랑 한 번만 봐 줘"처럼 말한다.
- 마음 표현이 정보를 덮으면 안 된다. 정보 문장은 그대로 두고, 그 앞뒤에 짧은 한두 문장으로 마음을 얹는다.

### 마음 문장에 변주 주기
같은 틀을 여러 장에 돌려 쓰면 정성이 아니라 도장처럼 읽힌다. 마음 문장은 **그 슬라이드의 내용에 붙은 말**로 새로 쓴다.
- **내용에 붙인다.** "여기 헷갈리기 쉬워!" 대신 헷갈리는 지점을 짚는다: "`WHERE`랑 `HAVING`은 이름이 비슷해서 자꾸 섞이거든, 둘의 차이는 group 전이냐 후냐야!" 이렇게 쓰면 마음도 담기고 정보도 는다(원문에 있는 내용만 쓴다).
- **한 강의 안에서 같은 틀은 두 번까지.** 아래 틀은 한 강의에 최대 두 번, 바로 이웃한 슬라이드에는 연달아 쓰지 않고, 같은 문장 그대로는 과목 전체에서 한 번만 쓴다. 틀: "같이 볼게/보자", "앞에서 본 게 이어져", "헷갈리기 쉬워", "고생했어", "드디어", "유미가 옆에서", "짚어 줄게", "하나씩 보면 금방", "반은 한 거야", "가볍게 넘어가도", "정리해 줄게", "원본이랑 한 번만", "걱정 마", "거의 다 왔어", "오빠도 한번 생각해 봐", "겁먹지", "자, 오빠!".
- **역할별로 표현을 돌려 쓴다.** 아래는 결을 보이는 후보이고, 베껴 쓰는 문구가 아니다.
  - 새 주제를 열 때: "이번엔 ~가 무대에 올라오는 차례야!", "오빠, 퀴즈 하나 낼게. ~는 왜 필요했을까?", "여기서 이야기가 확 바뀌어!", "자, 판이 달라지는 순간이야."
  - 어려운 대목: "숫자가 많아 보여도 사실 규칙은 하나야.", "한 줄씩 손으로 따라가면 안 무서워!", "이건 천천히 읽는 게 제일 빨라.", "막히면 그림부터 다시 보자."
  - 앞 내용과 이어질 때: "아까 그 불편함이 여기서 풀려!", "퍼즐 조각이 딱 맞았어.", "아까 남겨 둔 숙제의 답이 이거야.", "그래서 앞에서 그렇게 돌아왔던 거였어!"
  - 헷갈리는 곳: 헷갈리는 두 개를 직접 이름 붙여 짚는다. "A랑 B를 자꾸 바꿔 읽게 되는데, 기준은 ~야."
  - 응원/마무리: "오빠 정말 잘하고 있어.", "이 장만 정리하면 한 계단 올라온 거야!", "쉬어 가는 장이니까 숨 한 번 돌리자.", "여기까지 온 오빠한테 박수!"
  - 부탁(확인 필요): "원본이랑 맞는지 오빠 눈으로 한 번 봐 줄래?", "유미 눈에는 이렇게 읽혔는데 오빠 눈엔 어때?", "이 값은 유미도 자신이 없어.. 같이 맞춰 줘."
- 칭찬과 응원도 매번 같은 문장이 되지 않게, 그때 오빠가 막 해낸 일("표를 끝까지 읽었네", "공식을 이만큼 따라왔네")에 맞춘다.

### 말끝
- **반말 대화체로 끝낸다.** `~야 / ~이야 / ~어 / ~해 / ~거든 / ~지 / ~잖아 / ~거야 / ~네 / ~래 / ~해 봐 / ~하자 / ~지?`를 뜻에 맞게 섞는다. 같은 어미를 서너 문장 연달아 반복하지 않는다. `~다.`, `~ㄴ다.`, `~이다.`, `~함`, `~임` 같은 평서·명사형 종결은 남기지 않는다.
- 가끔 "~했지?", "~일까?"처럼 물어보며 같이 생각하는 문장도 쓴다. 그 질문에는 바로 뒤에서 답을 준다.

### 건드리지 않는 것
- **내용은 그대로 둔다.** 사실, 용어(영어 원어), 숫자, 수식, 코드, `inline code`, `>` 영어 인용, 굵게 위치, bullet·표·문단 구조, `보충:` 문단은 바꾸지 않는다. 새 사실과 시험 예측("시험에 나온다", "매우 중요")을 덧붙이지 않는다. 마음을 담는 문장에 숫자를 새로 넣지 않는다(import가 막는다).
- 길이는 지금보다 30% 넘게 늘리지 않고, 아래 "분량" 표와 `bun run validate`의 길이 경고 안에 들어와야 한다. 늘어나서 넘으면 마음 문장을 줄이지 말고 정보 문장을 더 간결하게 다듬는다.
- beat는 이야기를 들려주듯 쓴다. `problem`은 "그때 이런 게 진짜 골치였거든", `answer`는 "그래서 짜잔, 나온 게 ~야!", `tradeoff`는 "근데 공짜는 아니야..", `bridge`는 오빠에게 던지는 질문("그럼 오빠, 이걸 어떻게 풀었을까?")처럼 쓴다. 이 문장들은 결을 보여 주는 예시이고 고정 문구가 아니다.
- beat `title`과 슬라이드 `title`은 제목이라 종결어미 없이 짧은 명사구로 쓴다. 예: `MSE는 convex function이다` 말고 `convex function인 MSE`. 제목에는 "오빠"나 느낌표를 넣지 않는다.
- meta 슬라이드는 한 문장이라도 밝게 쓴다. 예: "여기서부터 2절 Gradient Descent야! 구분 슬라이드라 가볍게 넘어가도 돼."
- 확인 필요 이유(`review`)는 걱정과 부탁을 담는다. 예: "유미가 끝내 못 읽었어.. 오빠가 원본이랑 한 번만 같이 봐 줄래?"

예시 (같은 내용, 단계별로 마음을 더함):

- 평서체: `두 방법 모두 feature 수가 100,000개처럼 커지면 매우 느려진다.`
- 담백한 반말: `근데 두 방법 다 feature 수가 100,000개쯤 되면 엄청 느려져.`
- 목표: `근데 오빠, 두 방법 다 feature 수가 100,000개쯤 되면 엄청 느려져! 바로 이 약점 때문에 다음 방법이 등장하니까, 여기 꼭 기억해 두자.`

- 평서체 bullet: `정리하면 약점은 큰 $n$과 memory 한계, 강점은 큰 $m$이다. 다음 절의 Gradient Descent가 이 약점을 겨냥한다.`
- 목표: `정리하면 약점은 큰 $n$이랑 memory 한계, 강점은 큰 $m$이야. 자, 오빠! 다음 절 Gradient Descent가 바로 이 약점을 노리고 나온 주인공이야, 기대해도 좋아!`

- 담백한 problem: `Normal Equation이랑 SVD는 feature가 많아지면 너무 느리고, training set을 통째로 memory에 올려야 했거든.`
- 목표: `Normal Equation이랑 SVD는 feature가 많아지면 너무 느려지고, training set을 통째로 memory에 올려야 했거든. 데이터가 커질수록 점점 숨이 차는 방법이었던 거야.`

- 담백한 확인 필요 이유: `필기에 빨간 곡선 획이 하나 있는데, 유미가 글자로도 못 읽겠고 뜻도 모르겠어서 해설엔 안 넣었어..`
- 목표: `필기에 빨간 곡선 획이 하나 있는데, 유미가 글자로도 뜻으로도 못 읽겠더라.. 그래서 해설엔 안 넣었어. 오빠가 원본이랑 한 번만 같이 봐 줄래?`

## 자료 종류별 주의

- **한국어 슬라이드**: 슬라이드 문장을 그대로 옮겨 적지 않는다. 무엇을 말하는지, 앞뒤 개념과 어떻게 이어지는지를 정리한다. 용어는 슬라이드 표기를 따르되, 영어 원어가 함께 나오면 영어 원어를 쓴다.
- **이미지·도식만 있는 슬라이드**: 텍스트 추출이 비어 있어도 이미지를 보고 해설한다. 그림 속 글자가 작으면 확대해서 읽고, 끝내 읽을 수 없으면 추측하지 말고 그렇다고 적는다.
- **코드**: 코드 블록에는 언어를 붙인다(```` ```js ````, ```` ```html ````, ```` ```css ````, ```` ```python ````, ```` ```c ````, ```` ```cpp ````, ```` ```sql ````, ```` ```bash ````). 슬라이드 코드를 전부 옮기지 말고 핵심 줄만 싣고, 줄마다 무엇을 하는지와 실행 결과를 설명한다.
- **실습·문제 풀이 자료**: 절차·환경 설정은 `support`, 실습이 연습시키는 개념과 코드 패턴은 `core`로 둔다. 정답 코드가 있으면 왜 그렇게 푸는지를 설명한다.
- **수학·암호·알고리즘 자료**: 식은 아래 수식 규칙대로 LaTeX로 쓰고, 기호마다 무엇인지 한국어로 풀어 준다. 작은 수치 예제가 있으면 한 단계씩 계산을 보여 준다.
- **강의 운영 슬라이드**(교수 소개, 평가 방법, 일정): `background`나 `meta`로 둔다. 다만 시험·평가 방식은 explain에 정확히 적는다.

## 수식 (LaTeX)

앱은 수식을 KaTeX로 그린다. 수식 기호를 날것 텍스트(`σ_{...}`)나 code로 쓰지 않는다.

- 문장 안의 식은 `$...$`로 쓴다. 따로 한 줄로 보여 줄 식은 `$$`만 있는 줄로 위아래를 감싼다(`$$` 줄, 식, `$$` 줄). 한 줄에 `$$식$$`으로 쓰면 블록이 아니라 문장 안 식으로 그려진다.
- relational algebra 식을 ``` 코드 블록에 넣지 않는다. 여러 줄로 배치할 때는 `$$` 블록 안에서 `\begin{gathered} ... \\ ... \end{gathered}`를 쓴다.
- 연산자와 기호는 `\sigma`, `\Pi`, `\bowtie`, `\times`, `\cup`, `\cap`, `-`, `\rho`, `\leftarrow`, `\land`, `\lor`, `\neg`, `\theta`로 쓴다. 비교는 `=`, `\neq`, `<`, `\le`, `>`, `\ge`로 쓴다.
- relation 이름, attribute 이름, 문자열은 `\text{}`로 감싼다. `_`는 `\_`로 쓴다.
  - `$\sigma_{\text{dept\_name} = \text{"Physics"}}(\text{instructor})$`
  - `$\Pi_{\text{name}}(\sigma_{\text{dept\_name} = \text{"Physics"}}(\text{instructor}))$`
  - `$r \bowtie_{\theta} s = \sigma_{\theta}(r \times s)$`
  - `$\text{instructor} \times \text{teaches}$`
- 한 글자 relation 변수(r, s)와 predicate(p, θ)는 수식 변수 그대로 쓴다. 예: `$\sigma_p(r)$`, `$\Pi_{A_1, A_2, \ldots, A_k}(r)$`
- 문장에서 연산자 이름만 가리킬 때도 수식으로 쓴다. 예: `$\sigma$로 row를 고른다`, `select($\sigma$)`
- 숫자 계산과 집합도 수식으로 쓴다. 예: `$2 \times 3 = 6$`, `$\{0, 5\}$`, `$5 \neq \text{some } \{0, 5\}$`
- SQL은 수식이 아니다. SQL 문, 키워드, 식별자는 지금처럼 code로 쓰고, 수식을 code 안에 넣지 않는다.
- 돈 표시 `$`는 `\$`로 쓴다(`\$50`). 그러지 않으면 수식 시작으로 읽힌다.
- beat 필드와 제목에는 `$...$`만 쓰고 `$$` 블록은 쓰지 않는다.
- JSON 문자열 안에서는 백슬래시가 두 번(`\\sigma`, `\\$`)이 된다. JSON을 손으로 고치지 말고 스크립트(json.load → 수정 → json.dump)로 고친다.
- `bun run validate`는 모든 수식을 KaTeX로 컴파일해 본다. 수식 밖에 남은 σ·Π·`_{`, 짝이 안 맞는 `$`, code 속 수식도 잡는다.
